   `swift build -Xswiftc -warnings-as-errors` exit 0; `swift format lint -r Sources Tests`
   exit 0; `swift test` 569 core tests in 55 suites + 46 UI tests in 3 suites. The
   orchestrator's three runs: run 1 failed one unrelated 6a test (`createsOnAPrivateServer`,
   see *Open risks*), runs 2 and 3 passed fully, and the test alone passed. The fix worker
   reports three consecutive passing runs.
2. App bundle — **met.** `scripts/build-app.sh` exit 0 (worker, before and after the fix);
   `codesign --verify --deep --strict build/muxFinder.app` exit 0 (orchestrator, final tree);
   `codesign -d --entitlements -` shows `com.apple.security.automation.apple-events`; hardened
   runtime on both binaries (worker); Info.plist keys per D7; `muxfinder-launch` bundled in
   `Contents/MacOS/` beside the app, where the launch layer looks for it. The signing identity
   is picked by hash, since its name contains a non-ASCII character `codesign` did not match.
3. Screenshots — **met with a deviation.** `docs/screenshots/popover-states-{light,dark}.png`
   show 10 synthetic states (hosts and sessions, progress and errors, host problems, checking
   and empty hosts, search, no matches, no hosts turned on, unusable host list, iTerm2 check

4. Real binary from the shell — **met with a deviation.** Run directly (no LaunchServices):
   status item present, SIGTERM exit 0, no child or leftover process, no `hosts.json`
   (orchestrator re-checked: the support folder holds only `launch/`), no preference file. On
   macOS 27 the status item is drawn outside the app's process, so `CGWindowListCopyWindowInfo`
   shows nothing under the app's pid; the evidence is the new read-only
   `--report-menu-bar-item` flag (lists the app's own status-bar-level `NSApp.windows`).
5. Docs — **met.** New D22; Architecture, D11, D13, D20 sentences edited; `CLAUDE.md`

Not exercised for real: opening the popover, its key handling and Esc closing it (needs a

## Decisions

- **D22 — Menu bar app** (`PLAN.md`): `MuxFinderUI` library (model, `PopoverContent` pure
  value, views, preview fixtures) and a thin `MuxFinderApp` executable (`MenuBarExtra(.window)`,
  SF Symbol `terminal`, two app delegates); `AppModel` over an `AppEnvironment` seam; status
  and row text rules; iTerm2 contact and the cookie only on popover open while iTerm2 runs (or
  an attach); `PopoverWindowBridge` for visibility and keys; placeholder intents for Phases 9
  and 10 (no attach, launch or save); quit through `AppTermination.request()` with a 5 s
  shutdown deadline (a quit straight from a signal handler hung the app); preview fixtures in a
  plain `NSApplication` with no menu bar item.
- Review fix (D13, D20, D22 edited): closing the popover cancels the running attachment check
  and drops its follow-up, the cancelled check's result is ignored, and a reopen starts at once;
  an iTerm2 connection attempt whose callers were all cancelled stops before the cookie request
  and before connecting, while a caller joining before the cookie arrives keeps the attempt (no
  second cookie); the attachment index checks cancellation before each tmux connection;
  `AppModel.shutdown()` drops queued requests.

## Review

Codex → `ship-with-fixes`, 1 blocker, 0 should-fix; `docs/reviews/phase-8.md` (brief
`docs/reviews/phase-8.brief.md`). The blocker: closing the popover only queued
`popoverDidClose()`, so an attachment pass (cookie request, connection, identity questions)
could keep contacting iTerm2 after the popover closed. Fixed by a fix worker as above, with 8
regressions (6 core in `RefreshPopoverCloseTests.swift` and the client tests, 2 UI). Reverting
the whole fix failed 7 of 8; the eighth (`aCallerJoiningBeforeTheCookieKeepsTheAttempt`)
guards that the fix adds no second cookie request and passes on old code by design. Reverting
only the engine part failed all four close tests; only the client part, the three
"cookie pending" tests. Re-verified by the orchestrator (above). No re-review (one per phase).

## Open risks / deviations

- The worker's early preview runs made macOS record the menu bar item as hidden in the app's
  own preference domains; the worker deleted the two preference sets those runs had created
  (and their empty files). Preview mode no longer creates a menu bar item; the orchestrator
  found no `muxfinder` preference file afterwards.
- A cancelled caller leaves the iTerm2 connection attempt through a brief async hop; if the
  cookie arrives in that instant, one connection may still open, but no request is sent on it.
- The client gained a test-only counter (`attemptWaiterCount`).
- `createsOnAPrivateServer()` (6a, `TmuxCommandsTests.swift:710`) failed once in the
  orchestrator's first final-tree run: `#{pane_current_path}` read right after `new-session`
  did not match; passed in the next two full runs and alone. Code untouched by Phase 8; likely
  a race reading the pane's directory under load. Look there if the suite flakes.
- Popover open, key handling and Esc closing never ran for real (see above).
