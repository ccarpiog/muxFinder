# Phase 5b — remote attach over SSH

- **Risk:** high. **Worker model:** opus (implementation worker, then a fix worker for the
  review findings). Run: `/autoclaude-opus`, driven, 2026-10-22, which ended `BLOCKED` when
  iTerm2's API stopped answering. The final-tree real runs were made by hand the same
  afternoon, once the API answered again.
- **Scope:** the remote half of `PLAN.md` "### Phase 5" (its *Split* paragraph): the remote
  path in the coordinator and the helper, the 20 s `stillWaiting` budget, `AttachmentIndex`
  mapping for remote hosts, and `muxfinder-probe e2e-remote saturno-m4`.

## What was built

- The helper runs `/usr/bin/ssh -t -o ConnectTimeout=10 -- <dest> <D3 string>` (no
  BatchMode). The remote side runs the D4 guard check and then `exec`s tmux. ssh's exit 255 is
  classified from its relayed stderr. Every failure ends through the explanation, the wait for
  Return and the ≥10 s hold.
- Remote attaches get a 20 s budget to `confirmed`. Past it, with the launch tab open, the
  coordinator publishes `stillWaiting` (never success) and keeps watching once a second. It can
  still end `confirmed` later, or `failed`, or `waitLimitReached` at 300 s.
- `AttachmentIndex` maps remote hosts by the remote `uname -n`. The identity check also matches
  the host name. `detach(session:on:)` and focus-existing work remotely.
- The probe gained `attach --ssh` and `e2e-remote <dest>` (11 steps). `e2e-local` and
  `e2e-remote` share one harness, `Sources/muxfinder-probe/E2ERun.swift`.
- After the review: the `still waiting` step no longer logs in as anyone. A test-mode-only
  request field, `testLaunchDelaySeconds` (1–120), holds the helper before ssh starts, so no
  password prompt appears.

## Decisions

- New **D17** in `PLAN.md`, the remote attach design: ssh argv with `ConnectTimeout=10` and no
  BatchMode, the remote guard then `exec` tmux, exit 255 classified from relayed stderr, the 20 s
  budget, `stillWaiting` with a once-a-second watch that may still confirm, and
  `waitLimitReached` at 300 s. The remote check has no deadline of its own (a hang shows as
  `stillWaiting`). The stderr relay is bounded at 64 KiB per round with non-blocking writes;
  excess goes undisplayed but stays in the 16 KiB capture. Also in D17: the test-mode-only
  `testLaunchDelaySeconds`.
- D14, D15, D16 and *Verified facts* edited. iTerm2 hangs up a tab's process about 5 s after a
  forced close, so the coordinator waits 10 s for the helper's result after a waiting tab
  closes (`closedTabResultBudget`).
- The new `withAwaitedTask` cancels and awaits an unstructured task on every exit.

## Review

Codex → `ship-with-fixes` (`docs/reviews/phase-5b.md`), 0 blockers and 3 should-fix, all fixed
by the fix worker:

- **Should-fix:** unbounded stderr pumping and blocking terminal writes in
  `TerminalChildRunner` → a bounded, non-blocking relay; its regressions fail on the old code.
- **Should-fix:** the still-waiting step did not await its attach before cleanup →
  `withAwaitedTask`; its regressions fail on the old code.
- **Should-fix:** the step's real login as `nonexistent-muxfinder@saturno-m4` was outside the run
  rules → the test launch delay, covered by new tests.

## The iTerm2 stall

The third real `e2e-remote` run (pre-review tree, after two small edits) passed steps 1–9, then
iTerm2's API stopped answering in step 10. A read-only `sample` showed iTerm2's main thread
idle in its event loop (no modal) and all 64 GCD worker threads blocked in AppKit's
`-[NSAnimation _runBlocking]`. `iterm2 status` exited 75 at about 11:15 and did not answer at
11:45–11:53, so the run stopped as `BLOCKED`.

It cleared without a restart. When checked again in the early afternoon (before 13:46) `iterm2
status` connected, iTerm2 was the same process (up since 2026-10-21 19:27), and `ps -M` listed
18 threads. A person ended run 3's leftover launch tab at 13:46, around the start of the first
final-tree run (its ssh ended by SIGINT, the helper exited 130), and its unread result file
was removed from the launch directory. The cause is
still unknown; see *Consequences*.

## Consequences for later phases

- The iTerm2 API stall is unexplained. It can happen without a modal dialog and can clear on
  its own. Every real run should check `iterm2 status` and iTerm2's thread count before and
  after, and stop on a timeout.
- The 5 s between a forced tab close and the end of its process is iTerm2's: it showed with the
  helper alone in its launch delay, not only with ssh.
- `withAwaitedTask` has no time limit of its own; it relies on the coordinator's 10 s request
  timeouts and cancellable sleeps.
- The three pre-review `e2e-remote` runs each made one real login attempt to `saturno-m4` as
  `nonexistent-muxfinder`; nothing in the code does that any more.
