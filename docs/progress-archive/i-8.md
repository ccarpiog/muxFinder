## Decisions

- The routing rule is generic: any `NSPopUpButton` first responder keeps ↑, ↓ and ⌥↓; Return
  still creates and Esc still closes the panel (or the open directory list first). While any
  menu of the app tracks, every key passes through, so the open host menu keeps its own keys and
  Esc closes only it. With the directory list open and Host focused, the list stays open with its
  highlight unchanged and keeps Return/Esc (D31).
- Keyboard navigation off: no change; Host is never forced into the loop (user decision).

## Deviations and open risks

- `window.selectPreviousKeyView(_:)` with Name's field editor first responder leaves the focus
  in Name; the diagnostic's main reading uses `selectKeyView(preceding:)` on the Name field,
  cross-checked with ⇧Tab's own action message; both land on the picker.
- SwiftUI builds no AppKit pop-up button in a panel that is never shown, so tests cannot pick
  from the real menu; the pick is tested through the picker's binding.
- Unverified until a real press (checklist 22): what ↑/↓ do on a closed picker (open the menu or
  step the selection), whether ⌥↓ does anything there, whether the menu's tracking notifications
  fire for this picker in a non-activating panel, and VO-Space.
