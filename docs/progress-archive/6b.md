# Phase 6b — Move here (narrative)

Risk: high. Worker model: opus (implementation worker, then a review fix worker). Plan:
`PLAN.md` "### Phase 6", Split bullet 6b. Decision: **D21** in `PLAN.md` *Decisions*.

## Acceptance criteria (set before the worker)

- `moveHere` on the attach coordinator runs `attach-session -d` through the existing launch
  flow (guard, launch tab, connection confirmation, 10 s minimum tab age, single flight, typed
  failures), local and remote over ssh, reachable only with an explicit confirmation value.
- A normal attach never passes `-d` (argv and test-mode digest), locally or remotely; the remote
  move-here script stays static (D3).
- Request files without the new field still decode as a normal attach.
- Hermetic tests for the confirmation, `-d` present/absent, request decoding, the
  already-attached-here outcome and typed failures.
- Real `e2e-local` and `e2e-remote saturno-m4` pass with a Move here step: a harness-started
  plain control client is detached and the iTerm2 attachment remains; no leftovers.
- D21 recorded; `docs/TESTING.md` and `CLAUDE.md` step counts current.

## What was built

- `moveHere(_:confirmation:)` takes `MoveHereConfirmation.detachOtherClients(of: SessionKey)`
  (one case, no default); a confirmation for another session fails `moveHereNotConfirmed`
  before anything runs. The request carries `detachOtherClients` only when true; the helper adds
  `-d` only then; remotely a second static script (`moveHereScript`) is chosen. The test-mode
  argv digest records the attach child's argv and whether `-d` was used.
- Already attached here: the attachment check always runs; a session this Mac's iTerm2 already
  shows fails `alreadyAttachedHere(connectionID:owningSessionID:)` and runs nothing (`-d` would
  detach our own connection). After the review, a connection that cannot be ruled out (stale,
  timed out, non-UTF-8, unknown or ambiguous answers naming the target's server and session)
  fails `possiblyAttachedHere(unresolved:)`; an index failure fails `attachmentCheckFailed`.
- Cross-kind single flight (after the review): the coordinator tracks launches that may still
  attach a session. A move here waits for any of them, an attach only for move-here launches; a
  launch clears only on proof (request withdrawn before the helper took it, the helper's result,
  its connection, or its tab gone for 10 s). The wait is capped at the confirmation budget (15 s
  local, 20 s remote), then `earlierLaunchPending` with nothing run.
- E2E: a new Move here step (`e2e-local` now 16 steps, `e2e-remote` 17) starts a plain `tmux -u -C` client on the
  run's own session (remotely over ssh, BatchMode, no connection sharing), checks it gets
  `%exit` and exits by itself, that iTerm2's client is then the only one and still attached 2 s
  later, then detaches cleanly; on any failure the plain client is ended (stdin closed, then its
  process group). New file `Sources/muxfinder-probe/E2EControlClient.swift`.

## Review

1. Failed identification bypassed the already-attached check → `possiblyAttachedHere`.

## Open risks / deviations

- A connection whose exact answer names another server or session does not block a move here,
  even when `unknown` (refusing every `unknown` would block move here whenever another host's
  session is open); recorded in D21. Connections an index filter drops (only `e2e-local`'s)
  do not block it.
- A launch that never settles (for example a tab left waiting for a password) makes every later
  conflicting call for that session fail `earlierLaunchPending` until the tab ends or attaches.
- The ~120 s remote duration in `CLAUDE.md` / `docs/TESTING.md` is an estimate until the first
  real `e2e-remote` with the new step.
