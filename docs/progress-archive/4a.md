## What was built

- `Sources/MuxFinderCore/Launch/`:
  - `LaunchModels` — `LaunchRequest` / `LaunchResult` (Codable), local host kind with an
    extension point for Phase 5's ssh kind; no terminal content.
  - `LaunchStore` — `~/Library/Application Support/muxFinder/launch/` via `AppPaths` (root
    injectable): 0700 directory (symlink / foreign owner refused, loose mode tightened), 0600
    files, atomic writes, delete on read, 2-minute TTL with an injectable clock, stale-file
    sweep that never touches the `test-mode` marker, strict uuid validation.
  - `ExtendedACL` — strips extended ACLs from the launch directory on every open (refused with
    exit 73 if that fails) and from every new file before its first byte; a request carrying
    any ACL entry is refused and deleted.
  - `LaunchGuard` — static `/bin/sh` check script (D5 locator, D4 identity via
    `#{session_id}:#{pid}:#{start_time}:#{session_created}`), data only as argv; on success it
    prints the resolved tmux path.
  - `LaunchFailure` — typed failures and the pure exit-status mapping: `sessionGone` 64,
    `sessionChanged` 65, `tmuxMissing` 66, `checkTimedOut` 75, `interrupted(n)` 128+n,
    `sshFailed(class)` (type only), helper-side failures.
  - `TerminalChildRunner` / `LaunchHelper` — two children: the check runs in its own process
    group with a 10 s deadline (killed as a group on timeout or a forwarded signal), then tmux
    is spawned directly with argv `[tmux, -u, -CC, attach-session, -t, id]` on the inherited
    PTY. The helper ignores SIGHUP/SIGINT/SIGTERM for its life and forwards them, always writes
    the result file, explains failures and waits for Return only on a TTY.
  - `LaunchHelperPath` — D2 character rule and absolute-path check; locating the helper next
    to the running executable.
  - `LaunchArgvDigest` — test mode (`MUXFINDER_LAUNCH_TEST_MODE=1` or the `launch/test-mode`
    marker, created and removed through the store) writes an argv digest (count, byte lengths,
    hashes, uuid) so 4b can see how iTerm2 split the command.
- `Sources/muxfinder-launch/main.swift` — `muxfinder-launch attach <uuid>`.
- `Process/ProcessSupervisor*` — spawn helpers reusable without a new process group; the
  discovery runner's process-group kill semantics are unchanged.
- Tests: `Tests/MuxFinderCoreTests/Launch{Guard,HelperBinary,HelperPath,Helper,Models,Store}Tests.swift`,
  `LaunchTestSupport.swift`, `TerminalChildRunnerTests.swift` — hermetic, plus real tmux on a
  private `TMUX_TMPDIR` for gone / changed (pid, `session_created`) / tmux missing / no
  server, stalled-check timeout and signal-during-check with no descendant left.

## Decisions

- **D4 edited:** the guard reads `#{session_id}:#{pid}:#{start_time}:#{session_created}`
  because tmux 3.8 `display-message -t '$99'` for a missing id exits 0 with empty fields, so
  "gone" is read from the output. The few-millisecond check-then-attach window is recorded
  there (a session ending in it makes tmux exit 1; a server restart in it is caught by 4b's
  identity check through the connection).
- **D14 (new):** the launch protocol — exit codes, gone-vs-error rule, file and ACL rules,
  signal handling, the two-child design and the test-mode mechanism.
- Stricter ACL rule (any ACL entry on a consumed request → refuse) chosen because the macOS
  home-folder `everyone deny delete` ACL is not inheritable, so a normal home never trips it.

## Open risks

- `~/Library/Application Support/muxFinder` itself keeps any inherited ACL; only `launch/` and
  its files are covered. Relevant once `hosts.json` lands there (Phase 7).
- The helper was exercised under a `script` pseudo-terminal on a private tmux server, never
  inside iTerm2; 4b is the first real iTerm2 run.
- SwiftPM puts products in `.build/out/Products/Debug/` here (`.build/debug` links to it).
